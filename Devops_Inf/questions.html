DevOps Interview Questions & Detailed Answers

A practical study guide with interview questions, detailed answers, commands, and examples across AWS, Terraform, CI/CD, Docker, Kubernetes, and production troubleshooting.

1. AWS and cloud infrastructure

1. What are EC2, Lambda, and ECS? When would you use each?

Answer

  • Amazon EC2 provides virtual servers. You manage the operating system, installed software, network configuration, and scaling setup.
  • AWS Lambda runs code in response to events without requiring you to manage servers. It fits event-driven tasks such as processing an uploaded file or responding to an API event.
  • Amazon ECS orchestrates Docker containers. You define tasks and services, and ECS schedules and maintains containers. ECS can use EC2 capacity or AWS Fargate.
Example: A legacy application needing OS-level customization might run on EC2. A function resizing images after an S3 upload might run on Lambda. A continuously running containerized API might run as an ECS service.

Interview point: Compare workload and operational responsibility, not just definitions.

2. How do you create AWS infrastructure?

Answer

Use Infrastructure as Code (IaC), such as Terraform or AWS CloudFormation, to define resources in version-controlled files rather than relying only on manual console changes.

  1. Identify network, compute, storage, availability, security, and monitoring requirements.
  2. Write reusable IaC configuration and environment-specific variables.
  3. Run formatting, validation, and security checks.
  4. Review the plan and use approvals for production.
  5. Apply changes through a controlled pipeline and verify the resources.
Example: Terraform can define a VPC, subnets, security groups, an ALB, an Auto Scaling Group, and RDS. CI runs terraform fmt, terraform validate, and terraform plan; a reviewer checks the plan before an approved apply.
terraform init
terraform fmt -check
terraform validate
terraform plan -out=tfplan
# After review and approval:
terraform apply tfplan
3. How do you monitor an application?

Answer

Monitor infrastructure metrics, application metrics, logs, and user-visible symptoms. CloudWatch collects AWS metrics and logs; Prometheus commonly collects time-series metrics; Grafana provides dashboards and can display data from supported sources.

  1. Define indicators such as latency, error rate, traffic, and saturation.
  2. Collect infrastructure and application telemetry.
  3. Build dashboards for normal operation and incident diagnosis.
  4. Create actionable alerts and route them to an owner.
Example: If API 5xx errors rise, check ALB target response codes, target health, application logs, CPU/memory, and database latency. An alert should link to a dashboard and identify the service and environment.
4. How do you apply changes in AWS Cloud?

Answer

Use CI/CD with version-controlled application and infrastructure code. Changes should be reviewed, tested, and deployed through repeatable stages with an audit trail.

  1. A developer opens a pull request.
  2. Automated tests, linting, security checks, and IaC validation run.
  3. The pipeline creates a plan or release artifact.
  4. Approvals protect production where required.
  5. The pipeline deploys and verifies health; rollback steps are documented.
Example: A Terraform change adding an S3 lifecycle policy is reviewed in Git. CI generates a plan; after approval, the deployment job applies the reviewed plan and records the result.
5. How do you access instances that have private IP addresses only?

Answer

A private-only EC2 instance is not directly reachable from the public internet. Use an approved private path such as AWS Systems Manager Session Manager, a bastion host, or a VPN/Direct Connect connection. Prefer Session Manager when it meets requirements because it can avoid inbound SSH and bastion maintenance.

  1. Confirm the instance has the required IAM instance profile.
  2. Check connectivity to Systems Manager endpoints or the approved private path.
  3. Use least-privilege access and audit sessions.
  4. Avoid exposing SSH broadly to the internet.
Example: An engineer starts a Session Manager session through the AWS console or CLI using the organization's identity controls, without assigning a public IP to the instance.
6. What is VPC Peering, and when would you use it?

Answer

VPC Peering connects two VPCs for private IP routing. The CIDR ranges must not overlap, routes must be configured on both sides, and security groups/network ACLs must allow the traffic. Peering is not transitive.

Example: An app in VPC-A needs a private service in VPC-B. Create and accept the peering connection, add routes in both route tables, and allow only the required service port. For many VPCs requiring centralized connectivity, consider Transit Gateway.

2. Terraform and Infrastructure as Code

7. How do you connect Terraform with AWS?

Answer

Terraform uses the AWS provider to call AWS APIs. Authenticate through an approved credential chain—preferably an IAM role or short-lived credentials rather than long-lived keys embedded in files.

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
provider "aws" {
  region = "us-east-1"
}

The provider can use an execution role, environment credentials, or an approved AWS profile. Never commit credentials to Git.

Example: A CI job assumes a role with permission to manage only the staging resources. Terraform uses that identity to deploy the reviewed infrastructure changes.
8. What is the difference between count and for_each in Terraform?

Answer

Both create multiple instances. count identifies instances by numeric index; for_each identifies them by a stable map key or set member.

resource "aws_s3_bucket" "logs" {
  count  = 2
  bucket = "example-logs-${count.index}"
}

resource "aws_s3_bucket" "team" {
  for_each = toset(["payments", "orders"])
  bucket   = "example-${each.key}-logs"
}

Use count for a simple number of similar instances. Use for_each when each item has a meaningful identity. Keyed instances can avoid unwanted index shifts when one item is removed.

Example: For separate payments and orders buckets, for_each gives each resource a meaningful state address, so removing one key does not renumber the other.
9. How do you design a CI/CD pipeline for Terraform code?

Answer

Separate verification and planning from applying. Use a remote backend, locking where supported, limited permissions, code review, and production approvals.

  1. Checkout code and select the intended environment.
  2. Run formatting, validation, linting, and security checks.
  3. Initialize the backend and providers.
  4. Create a plan and publish it for review.
  5. Require production approval when appropriate.
  6. Apply the reviewed plan and verify results.
terraform fmt -check
terraform init
terraform validate
terraform plan -out=tfplan
terraform apply tfplan
Example: A pull request changes an ALB security group. The plan shows the exact ingress change. A reviewer checks that it does not expose unnecessary ports before approving deployment.
10. How do you securely pass secrets or sensitive data to Terraform?

Answer

Do not hardcode secrets or commit them to source control. Prefer role-based authentication and retrieve application secrets from a secrets manager at runtime. Terraform's sensitive = true masks normal CLI output, but does not guarantee the value is absent from state or every log.

  • Prefer IAM roles or short-lived credentials.
  • Store secrets in AWS Secrets Manager or an approved vault.
  • Encrypt and restrict remote state, which can contain sensitive values.
  • Limit access to pipeline logs and artifacts.
  • Rotate credentials and never print them in shell commands.
Example: The pipeline assumes an IAM role to create infrastructure. The application fetches its database password from Secrets Manager at runtime rather than receiving it as plain-text Terraform input.
11. What happens if the Terraform state file in S3 is accidentally deleted? How would you recover it?

Answer

The real AWS resources usually continue running, but Terraform may lose the mapping between resource addresses and existing infrastructure. Do not immediately run terraform apply, because it may propose duplicate resources.

  1. Pause automated applies and restrict changes.
  2. Check S3 versioning and restore the appropriate previous object version if available.
  3. Check backups and confirm the correct backend key/workspace.
  4. If state cannot be restored, carefully import existing resources into the correct resource addresses.
  5. Run a plan and review every proposed change before applying.
  6. Enable versioning, access controls, monitoring, and tested backups.
Example: A VPC exists but its state object was deleted. Restore the S3 object version if possible. Otherwise, define the matching Terraform resource and import its actual ID, then plan and reconcile before applying.
12. How do you manage Terraform state in a team environment?

Answer

Use a shared remote backend, restrict access, and enable state locking where supported. Separate state by environment or system boundary to prevent unrelated changes.

  • Keep state out of Git.
  • Encrypt state and apply least-privilege permissions.
  • Use locking to prevent concurrent state-changing operations.
  • Use a reviewable plan/apply workflow in CI/CD.
  • Back up state and test recovery procedures.
Example: Staging and production use separate backend keys and IAM permissions. If one pipeline holds the lock, a second apply waits or fails safely rather than changing the same state at the same time.

3. Git, Jenkins, and CI/CD

13. How do you integrate GitHub with Jenkins for automated builds?

Answer

Store code and the Jenkinsfile in GitHub. Configure repository access, a Jenkins Pipeline or Multibranch Pipeline job, and a webhook or another trigger. Jenkins checks out the relevant revision and runs the stages on a push or pull request.

  1. Configure repository credentials or an approved GitHub App.
  2. Set the repository and Jenkinsfile path in Jenkins.
  3. Configure webhook events and branch/PR discovery.
  4. Run tests, build an artifact, and publish results.
Example: A pull request triggers Jenkins to run unit tests and static analysis and report status to GitHub. A merge to the protected main branch triggers the release pipeline.
14. What is the difference between a Git webhook and Poll SCM in Jenkins?

Answer

A webhook is an event sent by the Git provider when a configured repository event occurs. Poll SCM makes Jenkins check the repository on a schedule to see whether changes are present.

  • Webhook: usually faster and avoids repeated polling, but requires a working event integration/connectivity path.
  • Poll SCM: can work when inbound webhook connectivity is unavailable, but adds periodic checks and possible delay.
Example: A push event can trigger a build quickly when GitHub can reach Jenkins through an approved integration. If Jenkins is private and no webhook route exists, scheduled polling may be used.
15. How do you manage Jenkins credentials securely and reference them in pipelines?

Answer

Store credentials in Jenkins Credentials or an approved external secrets manager, scope access narrowly, and reference credentials by ID. Never hardcode secrets in a Jenkinsfile or print them in logs.

withCredentials([
  string(credentialsId: 'api-token', variable: 'API_TOKEN')
]) {
  sh '''
    set +x
    ./deploy.sh
  '''
}

This binds a stored secret to an environment variable; the script must not print it. Use short-lived cloud credentials or role assumption when available.

Example: A deployment job obtains a registry credential at runtime, pushes the image, and keeps the secret out of source control and console output.
16. How do you troubleshoot a failed Jenkins pipeline?

Answer

Identify the first failing stage and examine its logs. Determine whether the cause is source code, dependencies, credentials, permissions, agent capacity, disk space, network access, or the target service. Avoid repeated retries without diagnosing the issue.

  1. Check the failed stage, exit code, timestamps, and error.
  2. Reproduce safely where possible.
  3. Fix the root cause and rerun.
  4. Verify downstream stages and add prevention such as tests, alerts, cleanup, or documentation.
Example: A Docker image builds successfully but cannot be pushed to ECR. Verify the AWS identity, repository and region, network access, and IAM permissions. Repair the credential source or permissions rather than repeatedly retrying.

4. Docker and Kubernetes

17. What is the difference between CMD and ENTRYPOINT in Docker?

Answer

ENTRYPOINT defines the main executable when the container starts. CMD provides default arguments or a default command. A common pattern is to use ENTRYPOINT for the executable and CMD for default arguments.

FROM alpine:3.20
ENTRYPOINT ["echo"]
CMD ["Hello from Docker"]

With no extra arguments, the container prints Hello from Docker. Supplying arguments at runtime replaces the default CMD arguments while keeping ENTRYPOINT.

Example: A Python worker could use ENTRYPOINT ["python", "worker.py"] and CMD ["--queue", "default"]. A deployment can override the queue without changing the executable.
18. How do you troubleshoot a Kubernetes pod in CrashLoopBackOff?

Answer

CrashLoopBackOff means a container repeatedly exits and Kubernetes delays restart attempts. It describes the restart pattern, not the root cause.

kubectl get pods -n <namespace>
kubectl describe pod <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --previous
  1. Review events and previous container logs.
  2. Check command/arguments, environment variables, mounted configuration, and secrets.
  3. Check probes and whether they are too aggressive.
  4. Check resource limits and OOMKilled status.
  5. Verify dependencies are reachable.
  6. Fix the cause and confirm the pod remains healthy.
Example: Logs show a required environment variable is missing. Correct the Deployment configuration, apply the change, then watch the rollout and inspect the new pod's logs.
19. Explain Persistent Volumes (PV) and Persistent Volume Claims (PVC).

Answer

A PersistentVolume (PV) represents storage available to a cluster. A PersistentVolumeClaim (PVC) is a workload's request for storage capacity and access mode. A StorageClass can define how storage is dynamically provisioned.

  • PV: the storage resource.
  • PVC: the application's request to use storage.
  • StorageClass: defines provisioning behavior.
Example: A database pod needs 20 GiB of persistent storage. Its PVC requests the capacity, Kubernetes provisions or binds a volume, and the pod mounts the claim. Replacing the pod does not itself erase the volume's data, though recovery depends on storage and reclaim policies.
20. How do you handle autoscaling in Kubernetes?

Answer

  • Horizontal Pod Autoscaler (HPA): changes pod replica count based on metrics such as CPU, memory, or custom metrics.
  • Vertical Pod Autoscaler (VPA): recommends or adjusts CPU/memory requests depending on configuration.
  • Cluster Autoscaler or node-provisioning tools: change node capacity when pods cannot be scheduled or nodes are underutilized.
Example: API CPU rises during a traffic spike. HPA scales replicas from 3 to 8. If the cluster has no room for new pods, a configured cluster autoscaler can add nodes. Correct resource requests, working metrics, suitable limits, and cloud quotas are essential.
21. How do you achieve URL/path-based routing in Kubernetes?

Answer

Use an Ingress resource with an Ingress controller, or an applicable Gateway API implementation. The controller directs HTTP/HTTPS requests to Services based on hostnames and paths.

Example: Route /orders to the orders service and /payments to the payments service. Install/configure the controller, point DNS to its entry point, configure TLS, and ensure the Services have healthy endpoints.

Troubleshooting: Check DNS, controller logs, Ingress rules, service ports, endpoint readiness, and application logs.

5. Production troubleshooting scenarios

22. An application behind an ALB returns HTTP 503. How would you troubleshoot it?

Answer

Check ALB and target-group health, then follow the request path to the application. A 503 can occur when the load balancer has no usable targets or when the backend returns the response, so determine where it originates.

  1. Check target health and ALB metrics such as HTTPCode_ELB_5XX_Count and HTTPCode_Target_5XX_Count.
  2. Review target health reasons, listener rules, target port, and health-check path/protocol.
  3. Verify security groups and network ACLs allow ALB-to-target traffic.
  4. Check application health, logs, capacity, and dependencies.
  5. Restore healthy capacity or roll back a harmful release, then validate client requests.
Example: A release changes the health endpoint from /health to /healthz, but the target group still checks /health. Targets become unhealthy. Correct the health check or app path, verify healthy targets, and confirm requests succeed.
23. Users report slow application performance. Which AWS metrics would you check first?

Answer

Establish whether the issue affects all users, a specific endpoint, or one environment, and compare the start time with deployments. Trace the request from load balancer through compute and database.

  • ALB: target response time, request count, target 5xx, ELB 5xx, healthy target count.
  • Compute: CPU, memory if collected, network, disk, process health, application logs.
  • RDS: CPU, connections, free storage, latency, database load, logs.
  • Application: latency, errors, slow requests, connection pools, dependency timing.
Example: ALB target response time rises while CPU and target count look normal. Logs reveal repeated slow database queries. Investigate database load and query performance instead of scaling EC2 blindly.
24. How would you perform a zero-downtime deployment in AWS?

Answer

Use a strategy that keeps healthy capacity serving requests while the new version is introduced. Options include rolling, blue-green, and canary deployments. The choice depends on platform, traffic management, compatibility, and rollback needs.

  1. Build and test an immutable artifact.
  2. Deploy to separate or limited capacity.
  3. Run health checks and smoke tests.
  4. Shift traffic gradually or replace instances in batches.
  5. Monitor errors and latency.
  6. Roll back if service indicators deteriorate.
Example: In blue-green deployment, the current version (blue) serves traffic while the new version (green) is deployed and tested. After validation, route traffic to green. If errors rise, switch back to blue, provided database changes remain compatible.

Caution: A traffic switch alone does not guarantee zero downtime; database changes must usually be backward-compatible during transition.

25. A Docker container keeps restarting in production. How would you identify the root cause?

Answer

Check exit status, restart count, logs, health checks, resource usage, and configuration. The same principles apply on a host, ECS, or Kubernetes, though the specific commands differ.

  • Inspect current and previous container logs.
  • Check exit code, OOM events, and memory limits.
  • Verify entrypoint, command, environment variables, mounted files, and secrets.
  • Check dependencies and health-check configuration.
  • Compare image digest and configuration with the last known-good release.
Example: The app exits with code 1 because a configuration file is not mounted. Logs reveal the missing file. Correct the deployment mount, redeploy, and verify that restart counts stop increasing.
26. Terraform apply fails midway after creating some resources. What would you do?

Answer

Do not assume the operation rolled back completely. Some resources may already exist. Inspect the error, state, and real infrastructure before retrying.

  1. Read the error and identify the failed resource/API call.
  2. Check Terraform state and AWS for resources already created.
  3. Fix the cause, such as permissions, quota, or invalid configuration.
  4. Run a fresh plan and review remaining changes.
  5. Apply only after confirming it will not damage existing resources.
  6. Import unmanaged resources if necessary; do not delete resources casually.
Example: Terraform creates a VPC and subnets but cannot launch EC2 because the account quota is reached. Resolve the quota, verify the existing resources are tracked, review a new plan, then apply.
27. A resource was manually changed in AWS, but Terraform reports drift. How do you resolve it?

Answer

Drift means real infrastructure differs from the declared configuration or recorded state. Decide whether the manual change is intended. If intended, update the code to represent it; if not, use Terraform to restore the desired configuration.

  1. Run a plan and identify differing attributes.
  2. Confirm with the owner whether the change was intentional.
  3. Update the configuration or plan a restoration accordingly.
  4. Review the plan and apply through the normal approval workflow.
  5. Investigate why the manual change bypassed controls.
Example: Someone opens SSH to all IP addresses on a security group. If unapproved, review a plan that restores the restricted CIDR and then apply it through the approved process.

6. Project and migration scenarios

28. How would you approach migrating a monolithic application to microservices?

Answer

Understand business capabilities, dependencies, data ownership, deployment constraints, and operational needs before splitting services. A gradual “strangler” approach moves one capability at a time while the monolith continues to operate.

  1. Map modules, APIs, data stores, and dependencies.
  2. Choose a capability that can be separated safely.
  3. Define API/data ownership, security, monitoring, and deployment.
  4. Build automated tests and CI/CD for the new service.
  5. Route controlled traffic to it and monitor behavior.
  6. Plan data migration and rollback, then repeat.
Example: Extract an order-notification module into a service with a clear API or event contract, retries, and monitoring. Keep order processing in the monolith until later migration steps.
29. After deploying an application, it becomes slow. How would you troubleshoot it?

Answer

Compare the slowdown with the deployment timeline. Check affected endpoints, latency, errors, logs, resource usage, dependencies, and deployment health. If the release causes severe impact, roll back through the approved process while preserving evidence for root-cause analysis.

  1. Confirm affected users/endpoints/environments.
  2. Compare before/after latency and error metrics.
  3. Check compute saturation, database queries, caches, connection pools, and external dependencies.
  4. Inspect code/configuration changes and logs.
  5. Roll back or disable the feature if needed.
  6. Verify recovery and document prevention steps.
Example: A new endpoint performs a database query for every item in a list. Traces reveal repeated queries. Roll back if impact is high, optimize the query/batching, test, and redeploy with latency monitoring.
